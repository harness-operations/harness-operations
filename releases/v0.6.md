# Harness Operations 0.6 — Systems Reference

Harness Operations 0.6 makes **Systems** the canonical entry point for understanding how agent Harnesses and adjacent components actually work, individually and together.

This release shifts the project from a Reference-Model-first presentation to a concrete, evidence-backed systems reference while preserving the Reference Model as deeper conceptual material.

## Systems

The new `systems/` reference covers contrasting operational architectures including:

- OpenAI Codex and Anthropic Claude Code;
- Claude Projects (redesigned beta), including coordinator-driven worker threads with configurable cloud or machine execution;
- Cisco Antares models and CLI;
- Cisco Foundry Security Spec;
- Playwright Test Agents;
- FireRed-OpenStoryline;
- Browser Use and Browser Harness;
- Computer Use across hosted, client-executed, and desktop-control placements;
- Realtime Voice across OpenAI Realtime and Pipecat;
- OpenAI Responses API background execution;
- Inspect AI as an agent-evaluation runtime.

## Operating arrangements and execution characteristics

The release distinguishes operating arrangements from other operational dimensions.

Operating arrangements now include:

- standalone bounded execution;
- interactive supervised work;
- embedded specialization;
- agent/Harness-as-tool delegation;
- durable artifact handoff;
- coordinator–worker threads;
- shared-state / queue workers;
- independent systems communicating across explicit interfaces.

Execution characteristics such as realtime, background, long-running, streaming, and configurable execution placement remain separate from workload and arrangement.

## Evidence and comparison semantics

0.6 tightens scope and evidence handling:

- product-family relationships are not promoted into exact machine relationships unless both endpoint scopes are established;
- Systems→comparison joins are configuration-safe across platform, plan, deployment, and material configuration;
- synthetic validation cases live under `tests/`, not the canonical reference;
- evaluator-owned controls remain attributed to the evaluator composition rather than the Harness under test;
- documentary relationships remain distinct from operation-specific tested interoperability;
- upstream product versions/revisions are recorded only where they materially scope evidence.

## Canonical structure

The concrete-reference split under `mappings/` is removed.

The repository now separates:

- **Systems** — concrete reference entries and operating arrangements;
- **Comparisons** — scoped capability/interoperability evidence;
- **Standards and Boundaries** — adjacent standards and interoperability semantics;
- **Reference Model** — descriptive conceptual vocabulary;
- **Tests** — synthetic validation and narrow executable checks.

Living canonical documents do not hardcode Harness Operations development/release status banners; Git tags and release metadata carry publication identity.

## Release verification

The release workflow validates:

- Systems index/schema and validation cases;
- comparison data/schema;
- the approved-artifact example tests;
- exact-version credential-free Harness interface smoke checks.

These checks verify repository consistency and the exact operations they execute. They do not constitute blanket product certification, security validation, or universal interoperability proof.

## Boundaries

This release does not introduce a Harness Operations wire protocol, certification scheme, universal product ranking, required orchestration architecture, or common lifecycle.

Follow-on work for independent A2A services, durable workflow runtimes, sandboxed code/data runtimes, mobile agents, robotics/embodied agents, and vertical-specific systems remains separate from this release.
